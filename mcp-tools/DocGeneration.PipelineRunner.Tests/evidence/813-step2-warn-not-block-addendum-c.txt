WHY THIS IS NOT A REVERSAL OF AD-029/ADDENDUM B
  Addendum B fixed a bug where non-empty ArtifactFailures with mapped exit 0 were
  NOT treated as a root (0/10 cascades caught). That fix — "any non-empty
  ArtifactFailures IS a root" — stands for every failure shape except ONE: a
  content/parameter-validation failure in ExamplePromptsStep that a) genuinely
  parsed an explicit "Invalid tools:" report from the validator (i.e. the
  validator process ran fine and told us exactly which tool(s) are missing a
  required parameter), and b) survived MaxValidationRetries retries. All other
  ArtifactFailure-producing paths (generator process failure/crash, missing
  per-tool output files, retry-generation process failure, missing regenerated
  output, and the validator "fallback" case where ParseInvalidTools finds
  nothing and we must assume ALL matching tools are invalid because the
  validator's own output/process could not be trusted) remain IsBlocking=true
  and continue to root exactly as Addendum B intended.

  M mcp-tools/DocGeneration.PipelineRunner/Steps/Namespace/ExamplePromptsStep.cs
      ValidationRun gains `bool IsFallback` (true only when the validator process
      failed AND ParseInvalidTools found no explicit "Invalid tools:" list, i.e.
      we fell back to "assume all matching/targeted tools invalid" — a hard,
      process-level uncertainty, NOT a genuine parsed content failure).
      ValidateWithRetriesAsync / RetryInvalidToolsAsync now track a per-command
      `Dictionary<string, bool> isBlockingByCommand`, seeded from the initial
      validation run's IsFallback and updated on every subsequent validator run
      for that command. A retry-generation PROCESS failure or missing
      regenerated output FORCES isBlocking=true for that command (these are
      unrelated hard failures that happen to surface mid-retry-loop; they must
      never be masked just because the command was originally a content
      failure). The final per-command ArtifactFailure for any still-unresolved
      command after retries are exhausted is created with
      isBlocking: isBlockingByCommand[command] (conservative default true if
      somehow absent).
  M mcp-tools/DocGeneration.PipelineRunner/PipelineRunner.cs
      IsFatalRoot's C2 clause changed from `artifactFailures.Count > 0` to
      `artifactFailures.Any(f => f.IsBlocking)`. C1 (nonzero mapped exit) is
      untouched. XML doc comment updated to describe the narrowing and why it
      does not affect any other step/scenario.

 ADDENDUM C-2 — squad review follow-up (Riley + Cameron must-fix findings)
--------------------------------------------------------------------------------
Independent squad review (reviewer-lockout: Riley/architecture, Cameron/test
strategy, Reeve/docs, all reviewing a change the Coordinator authored directly)
flagged that the ORIGINAL Addendum C left two behaviorally-important shapes
unpinned by a dedicated test, even though the production code already handled
them correctly by construction:

  1. Riley (APPROVE WITH COMMENTS) + Cameron (REQUEST CHANGES, must-fix): no
     test proved the intentional "latest validator observation wins" semantic
     for a command whose blocking status CHANGES across the retry loop (e.g.
     starts as a hard fallback failure, ends as a genuine non-blocking parse,
     or vice versa) — i.e. that isBlockingByCommand[command] is NOT sticky
     once set to true by an earlier hard/process failure.
  2. Cameron (must-fix): no test proved the validator "fallback" case (no
     parseable "Invalid tools:" report on ANY attempt) still ends up
     IsBlocking=true after retries are exhausted — this was previously only
     asserted "by construction" in prose, not by a running test.

FIX (tests only — no production code changed in this addendum)
  Added a new validator test double, FallbackThenGenuineParseRunner, to
  Unit/NamespaceStepTests.cs, and two new tests:

  + Step2_ExamplePrompts_ValidatorFallbackAfterRetriesStaysBlocking
      Validator returns a non-parseable ("fallback") failure on the initial
      call AND both retries (3 validator invocations total, all IsFallback=
      true). Asserts the step still reports Success=true, still records
      exactly one ArtifactFailure ("after automatic retries"), and that
      failure's IsBlocking is True — the hard/process-uncertainty shape
      remains fully blocking even after exhausting retries, exactly as
      Addendum C intended and AD-029/Addendum B originally required.

  + Step2_ExamplePrompts_LatestValidatorObservationDeterminesFinalBlockingStatus
      Validator returns a non-parseable ("fallback") failure on the INITIAL
      call only (IsFallback=true, seeding isBlockingByCommand=true), then a
      genuine, explicit "Invalid tools:" parse on BOTH retries (IsFallback=
      false on retries #1 and #2, still reporting the same command invalid).
      Asserts the final (and only) ArtifactFailure has IsBlocking=False —
      proving the LATEST validator observation about the command's current,
      already-regenerated content determines the final blocking status, and
      an earlier, since-superseded hard/process uncertainty does not
      permanently pin the command as blocking. This is the mixed-sequence
      case Riley and Cameron asked to have explicitly pinned.
