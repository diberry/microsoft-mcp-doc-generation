 THE MANDATED SEAM (AD-029 §A2 / ADDENDUM B) — as landed, verbatim
--------------------------------------------------------------------------------
  internal static bool IsFatalRoot(
      FailurePolicy policy,
      int mappedExitCode,
      IReadOnlyList<ArtifactFailure> artifactFailures)
      => policy == FailurePolicy.Fatal
          && (mappedExitCode != SuccessExitCode || artifactFailures.Count > 0);

  C1 = `mappedExitCode != SuccessExitCode` (hard Success=false failure, forced exit
       override, or fatal envelope-write failure).
  C2 = `artifactFailures.Count > 0` (the real Step-2 "validation failed after
       retries" shape: Success=true, mapped exit 0, yet durable per-artifact
       failures recorded — ExamplePromptsStep.cs:141). THIS is the clause the old
       exit-code-only trigger missed (16/17 corpus cases).
  C2 keys on ArtifactFailures, NOT on a failed ValidatorResult — so the intentional
  pre-AI non-fatal skip (Success=true + failed `pre-ai-validation` validator + EMPTY
  ArtifactFailures, from TryRunPreAiGateAsync) stays NON-fatal (T40 / PreAiValidation-
  GateTests green). The FailurePolicy.Fatal guard short-circuits first, so a Warn step
  is never a root even with artifact failures (T39 green).

  rootExit recompute (loop, D1) — load-bearing companion to the seam:
      var rootExit = stepOutcome.ExitCode != SuccessExitCode
          ? stepOutcome.ExitCode
          : MapStepFailureExitCode(FailurePolicy.Fatal, stepSucceeded: false,
                                   stepOutcome.Result.ExitCodeOverride);
  Without it, a C2-only root keeps its mapped exit 0 and worstRootExit = Worse(0,0) = 0,
  so the catalog would exit 0 despite a fatal root. The recompute yields FatalExitCode(1)
  (or HumanReviewExitCode(2) when the step forced a review override). This is exactly
  what the ONE authorized flip (PostValidatorTests :335, SuccessExitCode->FatalExitCode)
  now asserts GREEN.
